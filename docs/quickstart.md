# Быстрый старт

За семь шагов соберём рабочий `Check` на одном сюжете и разберём каждый кусок: откуда берётся роль, откуда право, что такое тип ресурса и звено, и кто за что отвечает. Пример можно скопировать и запустить как есть.

**Сквозной сюжет:** файловый сервис. В сервисе есть *документы*, документы лежат в *проектах*. Вопрос сервиса: «может ли пользователь записать в документ 42?»

## Установка

```bash
go get github.com/igor-kpsv/rolego
```

## Весь пример

Ниже — работающая программа: файл `main.go`. Читай её слева направо: комментарии «Шаг N» задают порядок. Остановись на комментариях, потом разбор по шагам — под кодом.

```go
package main

import (
	"context"
	"fmt"
	"log"

	"github.com/igor-kpsv/rolego"
)

// Шаг 1 — роли и права: константы твоего пакета.
// Роль отвечает на вопрос «кто ты?», право — «что тебе можно делать?».
const (
	RoleViewer  rolego.Role = 1 << iota // 1 — зритель
	RoleEditor                          // 2 — редактор
	RoleManager                         // 4 — менеджер проекта
)

const (
	PermRead  rolego.Perm = 1 << iota // 1 — читать
	PermWrite                          // 2 — изменять
)

// Шаг 2 — тип ресурса и сам ресурс.
// Kind — метка типа ресурса: «документ» = 1, «проект» = 2. Единого реестра
// нет: это твой домен, ты сам держишь метки согласованными во всём коде.
const (
	KindDocument rolego.Kind = 1 + iota // 1 — документ
	KindProject                         // 2 — проект
)

type Document struct {
	ID        uint64
	ProjectID uint64
}

// Шаг 3 — где ресурс лежит в иерархии. Scope — «адрес места»: тип места + номер.
// Документ — «дом», проект — «город», в котором дом стоит. Поэтому два адреса:
// {проект, номер проекта}, затем {документ, номер документа} (от крупного к самому ресурсу).
func scopes(d Document) []rolego.Scope {
	return []rolego.Scope{
		{Kind: KindProject, ID: d.ProjectID}, // проект №7 — город
		{Kind: KindDocument, ID: d.ID},       // документ №42 — дом
	}
}

// Шаг 4 — резолвер: твой код. Отвечает на один вопрос:
// «какие роли у субъекта на этом звене?» Звено приходит как Link.
type members map[string]rolego.Role

func (m members) RolesAt(_ context.Context, subj string, link rolego.Link) (rolego.Roles, error) {
	switch link.Kind {
	case KindDocument:
		return rolego.RolesOf(m[subj]), nil // роль на самом документе
	case KindProject:
		if subj == "boss" {
			return rolego.RolesOf(RoleManager), nil // роль менеджера на проекте
		}
	}
	return rolego.RolesOf(0), nil // ролей нет — пустая маска
}

// Шаг 5 — матрица прав: какая роль какие права даёт на данном типе ресурса.
var filePerms = rolego.Matrices{
	KindDocument: {
		RoleViewer:  PermRead,
		RoleEditor:  PermRead | PermWrite,
		RoleManager: PermRead | PermWrite,
	},
}

func main() {
	// Шаг 6 — сборка. Нужны все четыре куска сразу: без любого из них Check
	// не сможет ответить. Ось — порядок звеньев от самого глубокого к корню
	// и правило комбинации масок ролей.
	checker, err := rolego.New[string, Document](
		rolego.Type[string, Document](KindDocument),
		rolego.MapScopes[string, Document](scopes),
		rolego.Resolve[string, Document](members{"alice": RoleEditor, "bob": RoleViewer}),
		rolego.WithPolicy[string, Document](
			filePerms,
			rolego.NewScopeChain(
				rolego.Level(KindDocument), // самое глубокое звено — первым
				rolego.Level(KindProject),
				rolego.Combine(rolego.Nearest), // правило комбинации масок
			),
		),
	)
	if err != nil {
		log.Fatal(err)
	}
	if err := checker.Validate(); err != nil { // проверка политики на старте
		log.Fatal(err)
	}

	// Шаг 7 — вопрос: «может ли Алиса писать в документ 42?»
	doc := Document{ID: 42, ProjectID: 7}

	dec, err := checker.Check(context.Background(), "alice", doc, PermWrite)
	if err != nil {
		log.Fatal(err)
	}
	fmt.Println("alice:", dec.Allow()) // true — редактор документа

	dec, err = checker.Check(context.Background(), "bob", doc, PermWrite)
	if err != nil {
		log.Fatal(err)
	}
	fmt.Println("bob:", dec.Allow()) // false — зритель, писать нельзя

	dec, err = checker.Check(context.Background(), "boss", doc, PermWrite)
	if err != nil {
		log.Fatal(err)
	}
	fmt.Println("boss:", dec.Allow()) // true — роль менеджера поднята с проекта
}
```

Программа печатает:

```
alice: true
bob: false
boss: true
```

## Откуда что растёт: разбор по шагам

### Шаг 1. Роли и права

`RoleViewer`, `RoleEditor`, `RoleManager` — роли (кто ты), `PermRead`, `PermWrite` — права (что можно). И то и другое — константы со значением `1 << iota`: биты маски. Ты объявляешь их один раз в своём пакете; дальше работаешь именами, опечатку в имени компилятор поймает как ошибку — не будет тихого «`"editor"`».

Никаких строк и таблиц в базе. Право, как и роль, — просто число-бит.

### Шаг 2. Тип ресурса `Kind` и звено `Scope`

Строка `const KindDocument rolego.Kind = 1` объявляет **метку типа ресурса** «документ». Число 1 не имеет смысла само по себе — это просто постоянный идентификатор. Смысл появляется, когда одна и та же метка встречается в трёх местах:

1. в экстракторе — в звене `{Kind: KindDocument, ID: d.ID}`;
2. в матрице — как ключ `filePerms[KindDocument]` (запись «вот права для документов»);
3. в оси — как `rolego.Level(KindDocument)`.

А теперь главное: **«волшебного» превращения `KindDocument` в `Scope` нет**. Эту строку пишешь ты сам — в экстракторе `scopes`:

```go
{Kind: KindDocument, ID: d.ID}          // звено: документ с номером d.ID
```

`Scope` — это просто пара «тип + номер». `Kind: KindDocument` — «это звено типа „документ“», `ID: d.ID` — «конкретный документ №42». Собрать такую пару — тривиально; rolego не угадывает её за тебя, потому что не знает, как устроен твой `Document`.

`[]rolego.Scope{{...}, {...}}` — литерал слайса из литералов структур: список звеньев. В нашем примере два звена: проект и документ.

### Шаг 3. Адреса ресурса — почему роль может быть «на проекте»

rolego отвечает не «по документу», а «по месту в иерархии»: документ лежит в проекте. Чтобы библиотека понимала, где именно твой ресурс, ты даёшь ей функцию — «адресную книгу». На вход — твой `Document`, на выход — список адресов (`[]rolego.Scope`):

```go
{Kind: KindProject, ID: d.ProjectID} // адрес: «проект №7»
{Kind: KindDocument, ID: d.ID}       // адрес: «документ №42»
```

Адрес (`Scope`) — просто два поля: **тип места** (`Kind`) и **номер** (`ID`). Больше в нём ничего нет. Номер — твой `d.ID` из структуры, тип — твоя метка `KindDocument` из Шага 2.

Почему адресов может быть больше одного? Права можно выдать и на самом документе, и на проекте, в котором он лежит. В нашем примере у Алисы роль «редактор» на документе, а у босса — «менеджер» на проекте. Если бы адрес был один, роли «на проекте» не существовало бы.

Порядок в списке — от крупного места к самому ресурсу: сначала проект, потом документ. Это договорённость с библиотекой: так она узнаёт, что «документ вложен в проект».

Термин «звено», который встретится дальше в документации, — синоним слов «адрес» (`Scope`). Никакой магии: экстрактор — это и есть функция `scopes`, которую ты написал выше.

### Шаг 4. Резолвер — твой код

Резолвер отвечает на вопрос: «какие роли у субъекта на этом месте иерархии?». Для каждого адреса (`Scope`) рольго вызывает `RolesAt(ctx, subj, link)`. `link` — это и есть адрес («документ №42»), упакованный вместе с типом и глубиной; тебе сейчас нужен только `link.Kind` — тип места, и `link.Scope.ID` — номер места. Твой код достаёт маску ролей откуда угодно: из карты (как здесь), из запроса к БД, из правила «владелец ресурса».

В примере роль зависит от `link.Kind`: на самом документе смотрим в карту (`alice` → редактор), на проекте — своя логика (`boss` → менеджер). Если ролей нет — возвращай `rolego.RolesOf(0)`: пустое множество, нормальная ситуация.

### Шаг 5. Матрица — твоя политика

```go
var filePerms = rolego.Matrices{
	KindDocument: {
		RoleViewer:  PermRead,            // зритель читает
		RoleEditor:  PermRead | PermWrite, // редактор читает и пишет
		RoleManager: PermRead | PermWrite, // менеджер тоже
	},
}
```

«Что конкретная роль может на типе ресурса». `Matrices{тип: {роль: право, ...}}`. Запись `PermRead | PermWrite` — единственное место, где побитовый `|` уместен: собрать право из битов.

### Шаг 6. Сборка `New` — почему всюду `[string, Document]`

```go
checker, err := rolego.New[string, Document](...)
```

`string` и `Document` — параметры типов (**дженерики**). Их два:

- `S` — тип субъекта: здесь `string` (имя пользователя);
- `R` — тип ресурса: здесь `Document`.

Один раз объявил — и дальше компилятор следит, что ты задаёшь вопросы про субъекта-строку и ресурс-`Document`, и что резолвер с экстрактором согласованы. Каждая опция `New` — это функция вида `Option[S, R]`, поэтому в ней **повторяется та же пара типов**: `Type[string, Document]`, `MapScopes[string, Document]` и так далее. Это не магия и не опечатка — одна и та же пара, записанная в каждой опции.

Зачем четыре опции? Это четыре вопроса, без ответа на любой из которых библиотека не знает, что делать:

| Опция | Вопрос | Твой ответ в примере |
|---|---|---|
| `Type` | Для какого типа ресурса решаем? | `KindDocument` |
| `MapScopes` | Где у ресурса звенья? | функция `scopes` |
| `Resolve` | Откуда брать роли? | резолвер `members` |
| `WithPolicy` | Что кому разрешено? | матрица `filePerms` + ось `NewScopeChain(...)` |

Ось в `WithPolicy`:

```go
rolego.NewScopeChain(
	rolego.Level(KindDocument), // самое глубокое звено — первым
	rolego.Level(KindProject),  // затем родитель
	rolego.Combine(rolego.Nearest), // как объединять маски ролей
)
```

Она описывает ось уровней «документ → проект» и правило. Правило `Nearest` означает: **взять роль с самого глубокого звена, где она есть**; если на документе роли нет — подняться на проект.

### Шаг 7. `Check` — вопрос

```go
dec, err := checker.Check(ctx, "bob", doc, PermWrite)
```

Ответ — пара `(Decision, error)`. `dec.Allow()` превращает решение в `bool`. Внутри `Check` случается ровно тот конвейер, что описан на [главной странице](index.md):

1. `MapScopes(doc)` → `[{Kind: KindProject, ID: 7}, {Kind: KindDocument, ID: 42}]` — звенья от корня к ресурсу;
2. на каждом звене резолвер выдает маску ролей: bob на документе — зритель, на проекте — ничего;
3. `Nearest`: берется роль документа — зритель;
4. матрица `KindDocument`: у зрителя права `PermRead`, а запрошено `PermWrite` → **Deny**.

Для `boss` другой путь: на документе пусто, правило `Nearest` поднимается на проект, там — менеджер, у менеджера `PermWrite` → **Allow**. Тот же `Nearest`-подъём виден в третьей строке вывода.

## Политику лучше проверить при старте

`New` собирает из опций — но целостность проверяет `Validate()`: есть ли матрица для `Kind` из `Type`, не пуста ли ось, не забыт ли резолвер. Все противоречия собираются сразу одной ошибкой (`errors.Join`). Вызывай `Validate()` при старте приложения, чтобы политика не свалилась в бою.
