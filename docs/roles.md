# Роли и права

Роль — «кто ты», право — «что можно». Под капотом и то и другое — битовые маски, но работать с ними ты будешь методами, а не голыми битовыми операторами: методы читаются как намерение, а не как арифметика.

Сюжет прежний: файловый сервис, документы и проекты.

## Три типа: одиночная роль, право, множество

| Тип | Что это | Кто с ним работает |
|---|---|---|
| `Role` | Одна роль — константа `1 << iota` | Ты при объявлении ролей |
| `Perm` | Одно право — константа `1 << iota` | Ты при объявлении прав; `Check` |
| `Roles` | Множество ролей субъекта с методами | Резолвер возвращает, твой код проверяет |

```go
const (
	RoleViewer  rolego.Role = 1 << iota // зритель
	RoleEditor                          // редактор
	RoleManager                         // менеджер проекта
)

const (
	PermRead  rolego.Perm = 1 << iota // читать
	PermWrite                          // изменять
)
```

`1 << iota` — просто шаблон объявления констант: бит «съезжает» на каждом шаге. Один и тот же бит права (`PermRead`) может значить «читать» на документах и «просматривать» на проектах — права привязаны к типу ресурса через матрицу, об этом в [Скоупах и цепочках](scopes.md).

## Почему методы, а не операторы

Битовые операторы точны, но намерение в них не читается:

```go
// оператор: что происходит с маской?
mask |= RoleEditor

// метод: «добавь роль редактора» — понятно сразу
roles = roles.Add(RoleEditor)
```

У методов два свойства, которых нет у голых операторов:

- **Идемпотентность** — добавить роль дважды то же, что один раз; удалить отсутствующую — no-op.
- **Неизменяемость** — любой метод возвращает новое значение, исходное множество не трогается. Резолвер может спокойно накапливать роли по шагам, не боясь испортить общее состояние.

## Создание множества: `RolesOf`

```go
func RolesOf(role Role) Roles
```

```go
roles := rolego.RolesOf(RoleViewer)              // {зритель}
roles = roles.Add(RoleEditor)                    // {зритель, редактор}
```

`RolesOf(0)` даёт пустое множество — «ролей нет». Это штатная ситуация: `Check` превратит её в `Deny`.

**Профит:** стартовая точка резолвера — как правило, сначала пусто, потом роли по условиям.

## Проверки: есть ли роль

### `Has` — есть конкретная роль

```go
func (r Roles) Has(role Role) bool
```

```go
if roles.Has(RoleManager) {
	queue.Priority() // менеджеру — повышенный приоритет
}
```

Для составной маски ведёт себя как «хотя бы один бит» — совпадает с `HasAny`; имена различают намерение, а не поведение.

### `HasAny` — есть хотя бы одна из набора

```go
func (r Roles) HasAny(set Role) bool
```

```go
if roles.HasAny(RoleViewer | RoleEditor) {
	openPanel() // и зритель, и редактор его видят
}
```

То же самое через два `Has` прочитать легче, если набор из двух ролей:

```go
if roles.Has(RoleViewer) || roles.Has(RoleEditor) { ... }
```

**Профит:** «разрешить любую из перечисленных ролей».

### `HasAll` — есть все из набора

```go
func (r Roles) HasAll(set Role) bool
```

```go
if roles.HasAll(RoleEditor | RoleManager) {
	approveChanges() // нужны обе роли
}
```

Единственная проверка, требующая полного совпадения: «только если у субъекта есть все перечисленные роли».

## Изменение: собрать и отозвать

### `Add` — добавить роль

```go
func (r Roles) Add(role Role) Roles
```

```go
roles := rolego.RolesOf(0)
if doc.OwnerID == subj {
	roles = roles.Add(RoleViewer) // владелец — читатель
}
if editorOf[subj][doc.ID] {
	roles = roles.Add(RoleEditor) // ещё и редактор
}
```

**Профит:** накопительная сборка в резолвере — классика «проверил условие — добавил роль». Идемпотентно: повторный `Add` не меняет результат.

### `Remove` — отозвать роль

```go
func (r Roles) Remove(role Role) Roles
```

```go
roles = roles.Remove(RoleViewer) // доступ к чтению отозван
```

**Профит:** минус-операция без битов. Идемпотентно: удаление отсутствующей роли — no-op.

## `All` — «любое право»

Константа `rolego.All` — все биты прав сразу. Пригодится, когда важен сам факт «есть хоть какое-то право на ресурс», а не конкретное действие:

```go
decision, err := checker.Check(ctx, user, doc, rolego.All)
```

**Профит:** не надо перечислять все действия по одному.

## Иерархия ролей: `WithHierarchy`

Роли часто старшие по отношению к младшим: менеджер «включает» редактора, редактор — зрителя. Без иерархии это выражалось бы дублированием прав в каждой матрице (`RoleManager: <права RoleEditor> | extra`): не транзитивно и разрастается с каждой новой ролью.

Иерархия объявляется один раз:

```go
var hierarchy = rolego.Hierarchy{
	RoleEditor:  RoleViewer, // редактор включает зрителя
	RoleManager: RoleEditor, // менеджер включает редактора — и зрителя, транзитивно
}
```

И подключается опцией `WithHierarchy` при сборке `Checker` — в функции настройки сервиса:

```go
func setup() (*rolego.Checker[string, Document], error) {
	checker, err := rolego.New[string, Document](
		rolego.Type[string, Document](KindDocument),
		rolego.MapScopes[string, Document](scopes),
		rolego.Resolve[string, Document](resolver),
		rolego.WithPolicy[string, Document](perms, chain),
		rolego.WithHierarchy[string, Document](hierarchy),
	)
	if err != nil {
		return nil, err // цикл в иерархии — ошибка New (ErrHierarchyCycle)
	}
	return checker, nil
}
```

Что важно знать:

- **Матрицы остаются «свои права на роль».** Права предков добавляются роли при сборке, а не в момент `Check`: `Check`/`WhoCan`/аудит не меняют поведение.
- **Роль из иерархии без записи в матрице тоже наследует.** Объявил `RoleManager` в `Hierarchy`, но в матрице выписаны только зритель и редактор — менеджер всё равно получает их права.
- **`RolesFor` иерархию не раскрывает.** `RolesFor` возвращает маску ролей ровно так, как её выдал резолвер на звеньях — без добавленных предков. Иерархия расширяет только матрицы прав, в выдаваемые роли она не подмешивается. Вопрос «является ли роль наследственной для другой» решай сам по маске и своей иерархии.
- **Порядок опций неважен** — `WithHierarchy` до или после `WithPolicy`, результат одинаковый (расширение выполняется после всех опций в `New`).
- **Исходные матрицы не мутируются** — копия, переданная `WithPolicy`, остаётся нетронутой.

**Профит:** «старшая роль наследует права младших» без копипасты прав по матрицам и с транзитивностью по цепочке ролей.

## Один полный пример

Собираем множество ролей по условиям и проверяем его всеми методами:

```go
func roleOf(subj string, admins, editors map[string]bool) rolego.Roles {
	roles := rolego.RolesOf(0)
	if admins[subj] {
		roles = roles.Add(RoleManager)
	}
	if editors[subj] {
		roles = roles.Add(RoleEditor)
	}
	return roles
}

func main() {
	roles := roleOf("alice",
		map[string]bool{"boss": true},               // менеджеров мало
		map[string]bool{"alice": true, "bob": true}, // редакторов больше
	)

	fmt.Println(roles.Has(RoleEditor))                // true — редактор есть
	fmt.Println(roles.HasAny(RoleViewer | RoleManager)) // false — нет ни того ни другого
	fmt.Println(roles.HasAll(RoleEditor | RoleManager)) // false — менеджера нет

	extended := roles.Add(RoleViewer)      // добавили зрителя
	revoked := extended.Remove(RoleEditor) // отозвали редактора

	fmt.Println(revoked.Has(RoleViewer))    // true
	fmt.Println(revoked.Has(RoleEditor))    // false
	fmt.Println(roles.Has(RoleViewer))      // false — исходное множество не изменилось
}
```

## Шпаргалка

| Метод | Вопрос | Ответить «да», когда |
|---|---|---|
| `RolesOf(role)` | создать множество | нужно начать с роли или с пустого |
| `Has(role)` | роль есть? | у субъекта есть эта роль |
| `HasAny(set)` | хоть одна из набора? | разрешить любую из перечисленных |
| `HasAll(set)` | все из набора? | нужны все перечисленные роли |
| `Add(role)` | добавить роль | резолвер собирает множество по условиям |
| `Remove(role)` | отозвать роль | убрать роль из множества |
